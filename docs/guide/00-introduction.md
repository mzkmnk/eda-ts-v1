## イベント駆動アーキテクチャとは

### 定義

イベント駆動アーキテクチャ（EDA）は、**イベント**の生成・検出・消費を中心に設計されたソフトウェアアーキテクチャパターンです。

**イベント**とは、システム内で発生した状態の変化を表すものです。

```typescript
// イベントの例
const orderCreatedEvent = {
  source: "order-service",
  detailType: "OrderCreated",
  detail: {
    orderId: "ORD-12345",
    customerId: "CUST-001",
    items: [{ productId: "PROD-A", quantity: 2, price: 1000 }],
    totalAmount: 2000,
    createdAt: "2024-12-21T10:00:00Z",
  },
};
```

### EDA の 3 つの構成要素

```
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│   Producer  │────────▶│Event Router │────────▶│  Consumer   │
│ (イベント生成)│         │(イベント仲介) │         │(イベント消費) │
└─────────────┘         └─────────────┘         └─────────────┘
```

1. **Producer（プロデューサー）**: イベントを生成するコンポーネント
2. **Event Router（イベントルーター）**: イベントをフィルタリング・ルーティングする仲介者
3. **Consumer（コンシューマー）**: イベントを受け取り処理するコンポーネント

## 従来のアーキテクチャとの比較

### 同期型リクエスト/レスポンス（従来型）

```
┌────────┐  HTTP Request   ┌────────┐  HTTP Request   ┌────────┐
│Client  │────────────────▶│Service │────────────────▶│Service │
│        │◀────────────────│   A    │◀────────────────│   B    │
└────────┘  HTTP Response  └────────┘  HTTP Response  └────────┘
                                │
                                │ HTTP Request
                                ▼
                          ┌────────┐
                          │Service │
                          │   C    │
                          └────────┘
```

**特徴:**

- サービス間が密結合
- 呼び出し元は応答を待つ（ブロッキング）
- 1 つのサービス障害が全体に波及

### イベント駆動型（EDA）

```
┌────────┐                 ┌─────────────┐
│Client  │─────Event──────▶│             │─────Event──────▶ Service A
└────────┘                 │   Event     │
                           │   Router    │─────Event──────▶ Service B
                           │             │
                           └─────────────┘─────Event──────▶ Service C
```

**特徴:**

- サービス間が疎結合
- 非同期処理（ノンブロッキング）
- 障害の影響範囲が限定的

## EDA のメリット・デメリット

### メリット

| メリット             | 説明                                                                             |
| -------------------- | -------------------------------------------------------------------------------- |
| **疎結合**           | プロデューサーはコンシューマーの存在を知らない。新しいコンシューマーの追加が容易 |
| **スケーラビリティ** | 各コンポーネントを独立してスケール可能                                           |
| **耐障害性**         | 1 つのサービス障害が全体に波及しにくい                                           |
| **拡張性**           | 既存コードを変更せずに新機能を追加可能                                           |
| **リアルタイム処理** | イベント発生時に即座に処理を開始                                                 |

### デメリット

| デメリット           | 説明                                       |
| -------------------- | ------------------------------------------ |
| **結果整合性**       | データの一貫性が即座に保証されない         |
| **デバッグの複雑さ** | イベントフローの追跡が困難                 |
| **順序保証**         | イベントの処理順序が保証されない場合がある |
| **レイテンシの変動** | ネットワーク経由のため遅延が発生           |
| **学習コスト**       | 設計パターンの理解に時間が必要             |

## AWS における EDA の主要サービス

### Amazon EventBridge

イベントバスとして機能し、イベントのルーティングとフィルタリングを担当します。

```typescript
// EventBridgeへのイベント送信例
import {
  EventBridgeClient,
  PutEventsCommand,
} from "@aws-sdk/client-eventbridge";

const client = new EventBridgeClient({});

await client.send(
  new PutEventsCommand({
    Entries: [
      {
        Source: "order-service",
        DetailType: "OrderCreated",
        Detail: JSON.stringify({
          orderId: "ORD-12345",
          totalAmount: 2000,
        }),
        EventBusName: "order-events",
      },
    ],
  })
);
```

### AWS Lambda

イベントを受け取り処理するサーバーレス関数です。

```typescript
// Lambda関数の例
export const handler = async (
  event: EventBridgeEvent<"OrderCreated", OrderDetail>
) => {
  console.log("Received order:", event.detail.orderId);
  // 注文処理ロジック
};
```

### Amazon SQS

メッセージキューとして、イベントのバッファリングと順序制御を提供します。

### Amazon SNS

Pub/Sub メッセージングで、複数のサブスクライバーへの通知を実現します。

## 確認クイズ

以下の質問に答えて、理解度を確認しましょう。

<details>
<summary>Q1: EDAにおける「イベント」とは何ですか？</summary>

**A1:** システム内で発生した状態の変化を表すものです。例えば「注文が作成された」「支払いが完了した」などがイベントに該当します。

</details>

<details>
<summary>Q2: 同期型アーキテクチャと比較して、EDAの最大のメリットは何ですか？</summary>

**A2:** 疎結合性です。プロデューサーとコンシューマーが互いの存在を知らないため、独立した開発・デプロイ・スケーリングが可能になります。

</details>

<details>
<summary>Q3: EDAのデメリットとして「結果整合性」がありますが、これはどういう意味ですか？</summary>

**A3:** データの一貫性が即座に保証されず、最終的に一貫した状態になることを意味します。例えば、注文が作成されてから在庫が減るまでに若干のタイムラグが発生する可能性があります。

</details>
